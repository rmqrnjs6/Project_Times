## 목적과 확인한 사실

숫자나 문자열이 코드에 있다는 이유만으로 결함으로 간주하지 않았다. 이번 범위는 분석 서버 주소의 Spring 설정 주입과 중복 입력 정책의 관리 위치 통합이다. 성능 병목은 측정하지 않았으며 처리 속도나 메모리가 개선됐다는 주장은 하지 않는다.

확인한 문제: AnalysisService가 System.getenv().getOrDefault로 주소를 직접 읽었다. Spring 테스트 속성 app.analysis.base-url을 로컬 HTTP 테스트 서버로 지정해도 무시되어 ConnectException이 발생했다. 원래 58건은 PASS였지만 주소 주입과 JSON POST/준비 상태 응답을 확인하는 신규 2건은 수정 전 ERROR였다. 실패를 기록한 후 같은 테스트를 재실행했다.

중복 후보: 질문 2000자, 원문/해석 4000자, URL 2048자가 여러 서비스와 JSP에 반복되었다. 현재 값이 서로 틀린 버그는 확인되지 않았으나 한쪽만 바뀔 위험이 있어 통합했다. 외부 텍스트 20000바이트와 요청 32768바이트도 이름으로 의미를 드러냈다. 허용량 자체는 바꾸지 않았다.

## 실제 파일과 전후 차이

- AnalysisService.java: 환경변수 직접 조회 → 생성자의 @Value로 app.analysis.base-url 주입. 연결 3초/요청 5초는 이름 있는 Duration 상수로 분리했다. 재시도·리다이렉트 정책을 추가하지 않았다.
- application.properties: app.analysis.base-url=${ANALYSIS_URL:http://analysis:8000}. 기존 ANALYSIS_URL과 기본 주소를 유지하면서 Spring 설정으로 관리한다.
- InputLimits.java: 기존 정책값 5개를 상수로 정의하고 불변 Map을 화면에 제공한다. 런타임 환경변수로 허용량을 임의 확대하는 옵션은 만들지 않았다.
- TaskService.java, WorkbenchService.java, ExternalMaterialPolicy.java, RequestSizeFilter.java: 동일 숫자를 InputLimits로 참조. 읽기 버퍼는 REQUEST_BODY_BYTES + 1로 계산하며 초과 탐지를 유지했다.
- PageController.java → index.jsp: 모델 inputLimits를 전달하고 maxlength 및 안내 문구에 사용한다. 화면과 API가 같은 정책을 따른다. 화면 제한은 편의 기능이며 서버 검증이 권한 기준이다.
- AnalysisServiceTest.java: JDK 로컬 HTTP 서버와 Spring 컨텍스트로 설정 주입/실제 POST/503 준비 실패 경로를 검사한다. 외부 AI나 유료 서비스 호출은 없다.
- TaskMvcTest.java: 질문 2000/2001, 기록 4000/4001, URL 2048/2049 경계값 검사. 테스트 기대값은 원래 숫자를 명시해 정책이 바뀌면 발견할 수 있게 했다.
- SecurityMvcTest.java: 인증된 MVC 화면에 기존 제한값이 전달되는지 검사.
- scripts/integration_check.py: 실제 렌더링 HTML의 각 maxlength를 검사한다.
- README.md: 과거 통합 과정에 남은 문자 그대로의 \n을 실제 줄바꿈으로 고쳤다. 실행 동작 변경은 없다.

핵심 흐름: InputLimits → 서버 입력 검사 / MVC Model → JSP maxlength → 사용자 입력 → 서버 재검사 → 기존 저장 경로. 분석 호출은 Spring 설정 → 생성자 → HttpClient → 기존 /ready·/evaluate 경로다.

## 유지한 정책과 경계

reference-v1 가중치·점수 계산·R 반전·미확인 분모, 로그인 10회/15분과 BCrypt, Origin·CSRF·SameSite·same-origin 정책, 외부 출처 허용 목록, 소유자 격리, 기록 보존은 변경하지 않았다. TaskStore/Database의 SQL, 과거 Flyway 마이그레이션도 바꾸지 않았다. DB 제약 숫자는 스키마 이력이고 Nginx client_max_body_size 32k는 별도 계층의 방어이므로 제거하지 않았다. 목록 50개와 임대 120초도 이번 최적화 대상이 아니다.

## 복구와 학습 포인트

배포하지 않아 기존 실행 서비스를 되돌릴 작업은 없다. 작업 트리가 깨끗한 상태에서 이전 작업 브랜치로 전환하면 수정 전 코드를 검토할 수 있다. 이후 병합한 변경의 코드 복구는 해당 리팩터링 커밋을 git revert로 취소한다. DB 마이그레이션이 없어 DB 되돌리기는 필요 없다. 테스트 프로젝트의 볼륨을 삭제하는 명령은 실행하지 않았다.

환경마다 달라지는 주소는 설정 주입으로 관리하고, 정책 의미가 있는 숫자는 이름 있는 상수로 유지한다. 모든 숫자를 환경변수로 바꾸면 허용량과 DB 제약이 어긋날 수 있다. 클라이언트와 서버의 중복은 한 곳을 공유하되 DB 이력과 테스트의 독립 기대값까지 무조건 지우지 않는 것이 이번 학습 포인트다.
