# 검증 작업 검색·페이지 구분

기준일: 2026-11-09 KST. 기준 SHA d4a477a. 브랜치 feat/task-search-pagination.

## 설계와 범위

사용자가 지시한 다음 단계는 질문 검색과 페이지 구분이다. 브라우저에서 받은 최근 50개만 검색하면 오래된 작업을 놓친다. 따라서 소유자 조건을 유지한 서버 검색을 선택한다. 별도 검색 엔진은 현재 규모에 과하므로 추가하지 않는다.

기존 GET /api/tasks는 호환을 유지한다. 새 GET /api/tasks/page는 q(질문 부분 문자열, 최대 200자), page(0부터), size(기본 20, 1~50)를 받는다. 항목·현재 페이지·크기·전체 건수·다음 페이지 여부를 반환한다. 공백 검색어는 전체 조회, 영문 대소문자는 구분하지 않고 %, _, 따옴표를 문자 그대로 검색한다. 질문만 검색하며 근거 본문 검색은 후속 범위다.

건수와 목록은 동일한 읽기 스냅샷에서 조회하고 created_at DESC, id 순서를 유지한다. 화면에는 검색·초기화·이전·다음·건수를 제공하며 오래된 응답이 최신 검색을 덮어쓰지 않게 한다. 범위 밖 페이지는 빈 목록이다. 검색 실패 시 기존 목록을 보존하고 실패를 표시한다. 선택한 작업 상세와 입력 중 기록은 검색만으로 삭제하지 않는다.

## 실제 변경 위치와 이유

- TaskStore.java의 Page/page: 소유자 + POSITION(LOWER(?) IN LOWER(question)) 조건을 PreparedStatement로 바인딩한다. 기존 최근 50개 조회는 유지한다. 새 조회만 REPEATABLE_READ 트랜잭션으로 건수와 목록을 읽어 한 응답의 읽기 시점을 맞춘다.
- TaskService.java의 search: 검색어 공백 정리, 200자 제한, 음수/비정수 페이지와 1~50 범위 밖 크기 거부. 페이지 오프셋은 long 곱셈으로 정수 오버플로를 피한다.
- TaskController.java: /page 전용 경로와 기본값 0/20. 기존 /{id}, /api/tasks 목록, 저장/내보내기 계약은 보존한다.
- InputLimits.java와 index.jsp: 검색 입력 길이를 공유하고 검색/초기화/페이지 버튼과 결과 건수를 표시한다. 검색만으로 상세 선택과 수동 초안을 지우지 않는다.
- workbench.js: 성공한 조회의 페이지/검색어만 현재 상태로 확정한다. 요청 순번으로 늦은 응답/실패를 무시하고 실패 시 기존 결과를 유지한다. 이전/다음 버튼은 조회 중 잠그고 완료 후 실제 상태로 복구한다. 새 작업 등록 후에는 검색을 초기화해 새 작업을 선택한다.
- tests/helpers/workbench-harness.cjs: 두 화면 테스트에서 실제 JS를 실행하는 기존 모의 DOM/fetch 도우미를 공유한다. 테스트 전용 코드이며 제품에는 추가하지 않는다.
- CI: 검색 화면 테스트도 기존 Node 테스트 작업에서 실행하도록 추가했다.

## 한계·복구·학습

질문 문자열만 검색한다. 근거 본문/정정 기록 검색, 상태 필터, 전문 검색 엔진은 후속 범위다. 페이지 간에 새 작업이 추가되면 OFFSET 위치가 바뀔 수 있다. 한 응답의 일관성과 여러 요청 전체의 고정 스냅샷은 다르다. 대량 데이터의 부분 검색/COUNT 성능은 측정하지 않았으며 속도 개선 수치를 주장하지 않는다.

기존 실행 서비스는 미배포라 복구가 필요 없다. 향후 적용 후 코드를 되돌릴 때 이번 검색 변경만 revert하면 된다. 이번에는 새 마이그레이션이 없으며, 이전 기능의 V1~V5 파일과 원본 데이터는 유지한다. main 병합·기존 서비스 반영은 별도 승인 대상이다.

학습 포인트: 페이지 구분을 화면에만 구현하면 내려받지 않은 작업을 검색할 수 없다. WHERE 조건에는 검색어뿐 아니라 로그인 소유자도 포함해야 목록과 전체 건수 양쪽의 정보 노출을 막을 수 있다. 최신 요청 순번을 확인하는 이유는 늦게 도착한 과거 응답이 새 검색 결과를 덮어쓰지 않도록 하기 위해서다.
